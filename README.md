# Транслятор підмножини C на Flex/Bison

Лабораторна робота з системного програмування.

Проєкт реалізує синтаксичний аналізатор C-подібної імперативної мови на базі
Flex (лексер) і Bison (LALR(1)-парсер). Програма будує AST, виконує код
інтерпретатором, транслює його у C та показує дерево в браузері на d3.js.

## Можливості

- Лексичний аналіз (Flex): ключові слова, ідентифікатори, цілі та дробові числа, оператори, коментарі `//` і `/* */`, номери рядків для помилок.
- Синтаксичний аналіз (Bison): граматика підмножини C з пріоритетами операторів і розв'язаним dangling else, повідомлення про синтаксичні помилки з номером рядка.
- Побудова AST: один універсальний тип вузла `Node`.
- Семантика (інтерпретатор): типи `int` і `double`, функції, рекурсія, лінивi `&&` та `||`, помилки часу виконання.
- Генерація коду: трансляція AST у робочу програму на C.
- Візуалізація: експорт AST у JS-файл і інтерактивне дерево в браузері (d3.js).

## Мова

Підтримується така підмножина C:

- типи `int`, `double`, `void`; оголошення змінних `int x = 5;`, `double d;`
- функції з параметрами, `return`, виклики, рекурсія; виконання починається з `main`
- `if / else`, `while`, `for`, блоки `{ }`
- арифметика `+ - * / %`, унарний мінус
- порівняння `< > <= >= == !=`
- логіка: `&&`, `||`, `!`
- `i++` та `i--` (як окремий оператор)
- вбудований `print(вираз)`
- коментарі `//` та `/* ... */`

Приклад:

~~~c
int fact(int n) {
    if (n <= 1) { return 1; }
    return n * fact(n - 1);
}

int main() {
    int i;
    for (i = 1; i <= 5; i++) {
        print(fact(i));
    }
    double d = 7;
    print(d / 2);
    return 0;
}
~~~

### Граматика (скорочено)

~~~
program   : func_list
func      : type IDENT '(' params_opt ')' block
type      : int | double | void
stmt      : simple ';'
          | call ';'
          | return [expr] ';'
          | print '(' expr ')' ';'
          | if '(' expr ')' stmt [else stmt]
          | while '(' expr ')' stmt
          | for '(' simple ';' [expr] ';' simple ')' stmt
          | block
simple    : (порожньо)
          | type IDENT ['=' expr]
          | IDENT '=' expr
          | IDENT '++' | IDENT '--'
expr      : INUM | DNUM | IDENT | call
          | expr (+ - * / % < > <= >= == != && ||) expr
          | '-' expr | '!' expr | '(' expr ')'
call      : IDENT '(' [args] ')'
~~~

Повна версія знаходиться у `src/lang.y`.

## Збірка

Потрібні `flex`, `bison` 3.x, `gcc` (або `clang`) і `make`.

macOS (Homebrew):

~~~
brew install flex bison
export PATH="$(brew --prefix bison)/bin:$(brew --prefix flex)/bin:$PATH"
cd src && make
~~~

Системний bison на macOS має версію 2.3 і застарів. Homebrew ставить новий bison
як keg-only (без символічних посилань), тому його шлях додається в `PATH` вручну.

Linux (Ubuntu): `sudo apt install flex bison gcc make`.

Очищення: `make clean`.

## Використання

Усі команди виконуються з каталогу `src`.

~~~
./lang ../examples/test3.lang                    # виконати інтерпретатором
./lang --tree ../examples/test3.lang             # вивести AST текстом
./lang --c ../examples/test3.lang > out.c        # згенерувати C
gcc out.c -o out && ./out                        # зібрати і запустити згенерований код
./lang --web ../examples/test3.lang > tree.js    # AST для браузера
open viewer.html                                 # відкрити візуалізацію (macOS)
~~~

Для візуалізації потрібен інтернет (d3.js завантажується з CDN).
У браузері: колесо миші змінює масштаб, перетягування рухає дерево,
клік по вузлу згортає або розгортає гілку.

Швидка демонстрація всіх режимів:

~~~
./demo.sh examples/test3.lang
~~~

## Структура проєкту

- `src/lang.l` лексер (Flex)
- `src/lang.y` граматика, семантичні дії, побудова AST (Bison)
- `src/ast.h`, `src/ast.c` вузол AST, конструктори, друк дерева
- `src/interp.h`, `src/interp.c` інтерпретатор
- `src/codegen.h`, `src/codegen.c` генератор коду на C
- `src/ast_json.h`, `src/ast_json.c` експорт AST для d3.js
- `src/main.c` розбір аргументів і вибір режиму
- `src/viewer.html` візуалізація (d3.js)
- `src/Makefile` збірка
- `examples/` тестові програми
- `demo.sh` скрипт демонстрації

## Як це працює

~~~
текст програми -> [Flex: лексер] -> токени -> [Bison: парсер] -> AST
AST -> інтерпретатор          -> виконання
AST -> генератор C            -> out.c -> gcc -> виконуваний файл
AST -> експорт JSON           -> viewer.html (d3.js)
~~~

Парсер викликає `yylex()` щоразу, коли йому потрібен наступний токен.
Усі три результати (виконання, C, візуалізація) отримуються обходом
одного й того самого дерева.

## Хід розробки по етапах

Проєкт розроблявся поетапно, після кожного етапу існувала робоча програма.

### Етап 1. Калькулятор

Перший парсер одразу обчислював вираз у діях `$$ = $1 + $3`. Це дозволило
зрозуміти зв'язок між Flex і Bison: лексер повертає номер токена, текст
лексеми лежить у `yytext`, а значення токена передається в парсер через `yylval`.
Пріоритети операторів задавалися рядками `%left` і `%right`.

### Етап 2. Побудова AST

Замість обчислення дії парсера тепер створюють вузли дерева. Дерево
будується знизу вгору: спочатку листки (число, змінна), потім з них
складаються батьківські вузли. Дужок в AST немає: групування закодоване
самою структурою дерева. Для `2 + 3 * 4` вузол `*` лежить глибше за `+`.

Усі вузли мають один тип `Node` з полями `a`, `b`, `c`, `d` (діти) та `next`
(наступний елемент списку: оператор, аргумент, параметр, функція).

### Етап 3. Інтерпретатор

Файл `interp.c` рекурсивно обходить AST двома функціями:

- `eval(вузол, фрейм)` обчислює вираз і повертає значення;
- `exec(вузол, фрейм)` виконує оператор; повертає 1, якщо виконався `return`,
  і цей прапорець «розмотує» вкладені цикли та блоки.

Значення це пара «число + ознака int». Завдяки цьому `7 / 2` дає 3
(цілочисельне ділення, як у C), а `7.0 / 2` дає 3.5. При присвоєнні
значення приводиться до типу змінної.

Кожен виклик функції створює власний `Frame` зі змінними, тому рекурсія
працює і `n` на різних рівнях не змішуються. Оператори `&&` та `||`
обчислюються лінива, як у C.

### Етап 4. Генерація коду на C

Файл `codegen.c` обходить те саме AST і друкує еквівалентну програму на C.
Особливості:

- усі операції виводяться в дужках, щоб порядок обчислень збігався з деревом;
- спочатку генеруються прототипи функцій, тож порядок функцій не має значення;
- `print(x)` перетворюється на макрос `PRINT(x)`, який через `_Generic` (C11)
  обирає формат `%d` або `%g` за типом виразу;
- `i++` до цього моменту вже розгорнуте в `i = i + 1`.

### Етап 5. Візуалізація

`ast_json.c` обходить AST і друкує вкладений об'єкт `{name, kind, children}`
у файл `tree.js`. `viewer.html` підключає його разом з d3.js: `d3.hierarchy`
будує ієрархію, `d3.tree` обчислює координати без перекриття, `d3.zoom` дає
масштабування. Вузли розфарбовані за полем `kind` (число, змінна, операція,
оператор, керування, блок).

### Етап 6. Розширення до підмножини C

Додано типи, функції, `for`, логічні оператори, `++`, `--`, `%`, коментарі
`/* */`. Лексер розрізняє цілі (`INUM`) і дробові (`DNUM`) числа, тому парсер
знає тип літерала.

## Теорія: як працює Yacc/Bison

**Розподіл ролей.** Лексер працює з регулярними мовами (скінченний автомат)
і не розуміє вкладеності, тобто не знає, що дужки мають бути парними.
Парсер працює з контекстно-вільною граматикою, яка описує вкладені структури.

**LALR(1).** Look-Ahead LR з одним токеном випередження. Це висхідний
(bottom-up) розбір: читання зліва направо, побудова правого виводу
у зворотному порядку.

**Як працює парсер.** Bison будує з граматики таблиці ACTION і GOTO.
Функція `yyparse` тримає стек станів автомата (разом із семантичними
значеннями). На кожному кроці за станом на вершині та поточним токеном
вона обирає дію:

- `shift`: покласти токен на стек і перейти в новий стан;
- `reduce`: замінити на стеку праву частину правила його лівою частиною
  (при цьому виконується семантична дія, `$$` обчислюється з `$1..$n`);
- `accept` або `error` (тоді викликається `yyerror`).

Семантичні дії виконуються саме в момент згортки, коли всі символи правої
частини вже на стеку. Тому AST будується знизу вгору.

**LALR проти інших.** LR(1) має найбільші таблиці, бо стани розрізняються
за lookahead. SLR простіший, але слабший, бо використовує множини FOLLOW.
LALR зливає стани LR(1) з однаковим ядром (набором пунктів): таблиці малі,
потужність майже як у LR(1). Злиття теоретично може створити reduce/reduce
конфлікти, яких у LR(1) не було.

**Конфлікти.**

- *Shift/reduce.* За замовчуванням Bison обирає shift і попереджає.
  Розв'язується пріоритетами й асоціативністю (`%left`, `%right`,
  `%nonassoc`, `%prec`): порівнюється пріоритет правила і токена, при
  рівності вирішує асоціативність (`%left` дає reduce, `%right` дає shift,
  `%nonassoc` дає помилку).
- *Reduce/reduce.* Bison обирає правило, записане в граматиці раніше.
  Зазвичай це ознака помилки в граматиці, яку краще виправити.

**Dangling else.** У `if (a) if (b) x; else y;` незрозуміло, до якого `if`
належить `else`. У стані після `IF '(' expr ')' stmt` парсер може згорнути
внутрішній `if` або зсунути `else`. Розв'язано двома рядками:

~~~
%nonassoc IFX
%nonassoc ELSE
~~~

і `%prec IFX` у правилі `if` без `else`. Токен `ELSE` має вищий пріоритет,
тому виграє shift, і `else` належить найближчому `if`.

**Унарний мінус.** Правило `'-' expr %prec UMINUS` отримує пріоритет
вигаданого токена `UMINUS`, бо інакше воно мало б пріоритет бінарного `-`.

**Власна граматика не має конфліктів.** Це видно з файлу `lang.output`
(команда `bison -v lang.y`).

### Експерименти з конфліктами

Конфлікти можна відтворити на власній граматиці (у тимчасовому каталозі,
щоб не змінювати проєкт):

~~~
mkdir -p /tmp/conf && cd /tmp/conf
# без розв'язання dangling else:
sed -e '/%nonassoc/d' -e 's/ %prec IFX//' ../src/lang.y > lang.y
bison -v -Wcounterexamples lang.y
# без пріоритетів операторів:
sed '/%left/d' ../src/lang.y > lang.y
bison -v lang.y
~~~

Перший запуск повідомляє про shift/reduce конфлікт на токені `ELSE`, другий
про велику кількість shift/reduce конфліктів між операторами.

## Проблеми, які виникли, і їх розв'язання

1. **Старий bison на macOS.** Системний `bison --version` показував 2.3.
   Причина: установка через Homebrew спершу була скасована, а після неї новий
   bison (keg-only) не потрапляє в `PATH` автоматично. Розв'язання: `brew install
   flex bison` і додавання `$(brew --prefix bison)/bin` на початок `PATH` у
   `~/.zshrc`.
2. **`%option noyywrap`.** Без цієї опції лінкування вимагає функції `yywrap`.
   Для одного вхідного файлу достатньо вимкнути її опцією.
3. **Ключові слова й ідентифікатори.** Правила для `if`, `while`, `int` стоять
   у лексері вище правила ідентифікатора: при однаковій довжині збігу Flex
   обирає правило, записане раніше. Тому `int` це ключове слово, а `integer`
   (збіг довший) ідентифікатор.
4. **Цілочисельне ділення.** У C `7 / 2` дає 3, а у розрахунках на `double` було
   б 3.5. Тому інтерпретатор зберігає тип значення, а в згенерованому C числа
   виводяться як цілі або дробові відповідно.
5. **Формат `print` у згенерованому C.** Формат `%d` або `%g` залежить від типу
   виразу. Замість власного виведення типів використано `_Generic` у макросі.
6. **Порожні частини `for`.** Для порожньої ініціалізації чи кроку правило
   `simple` дає `NULL`, а для порожньої умови правило `opt_expr` дає `NULL`;
   інтерпретатор і генератор перевіряють це явно.

## Тестування

Тестові програми лежать у `examples/`.

- `test1.lang`: змінні, `if`, `while`. Очікуваний вивід: `11`, потім `5 4 3 2 1`.
- `test2.lang`: факторіал циклом. Очікуваний вивід: `120`.
- `test3.lang`: функції, рекурсія, `for`, типи `int` і `double`, `&&`, `!`, `%`.
  Очікуваний вивід: `1 2 6 24 120 3 3.5 3.5 1 3`.

Перевірка збігу інтерпретатора і згенерованого C:

~~~
cd src
./lang ../examples/test3.lang
./lang --c ../examples/test3.lang > out.c && gcc out.c -o out && ./out
~~~

Обидва виводи однакові.

## Обмеження

- Немає масивів, вказівників, структур, рядків і препроцесора.
- Немає `break`, `continue`, `+=`, `-=`, глобальних змінних.
- `++` і `--` підтримуються лише як окремий оператор (не всередині виразу).
- В інтерпретаторі область видимості одна на функцію, а не на блок (у C
  змінна з заголовка `for` видима лише в циклі).
- Ділення на нуль у згенерованому C для цілих чисел призводить до аварійного
  завершення, а інтерпретатор виводить повідомлення і продовжує.
- Генерований код використовує `_Generic`, тому потрібен компілятор C11 і новіший.
- Візуалізація потребує інтернету для завантаження d3.js.
